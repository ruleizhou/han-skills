# Step 8B: 动态复现与回归评估（条件触发）

本步骤在修复方案通过 8A 对抗验证后执行。目的是**用动态复现验证静态根因**，并用回归测试锁定修复——补 analyzer 纯静态分析的短板。

## 红线（必须先读）

本步骤是**后置增强，不是前置门控**。analyzer 的根基是静态分析已发生的 dump；大量内核 crash（一次性 ramdump、硬件瞬态）物理上不可复现。本步骤只在"可复现类"触发，不可复现类**快速跳过并记录**，**不影响**根因结论的置信度——根因置信度始终来自 Step 5-7A 的静态证据链 + 对抗验证。

## 1. 触发判断：要不要建复现回路？

按根因性质判断：

| 根因性质 | 触发？ | 理由 |
|----------|--------|------|
| **动态行为类**：竞态/并发（KASAN UAF、ABBA 死锁、SLUB redzone）、内存生命周期、压力/时序相关、性能回归 | ✅ **执行本步骤** | 静态看不全触发时序，必须动态复现才说得清根因 + 验证修复 |
| **静态逻辑类**：错误路径漏释放、NULL 解引用、初始化顺序错误、API 误用 | ⚪ **跳过** | 静态证据链 + 对抗验证已足够，复现是锦上添花 |
| **硬件瞬态类**：单次 SEU、DRAM bit flip、一次性 ramdump 无复现路径 | ⚪ **跳过并标注** | 物理不可复现，在报告中标注"静态置信度" |

**判断依据**：取 Step 7 的根因分类（竞态/错误路径清理/UAF/初始化顺序/锁顺序/其他）+ Step 0 的场景描述。根因分类为"竞态/UAF/锁顺序"，或场景含"偶发/压力/高负载/低概率/长时间运行"关键词 → 动态行为类。

**跳过时**：在报告中注明"未触发动态复现（原因：<静态逻辑类 / 硬件瞬态类>）"，直接读取 `workflows/step-09-report.md`。

## 2. 评估能否建复现回路

从以下手段中选内核适用的（优先级从上到下）：

1. **触发脚本**：构造能稳定触发 crash 路径的 ioctl / sysfs / 系统调用序列
2. **压力复现**：开 KASAN 使能镜像 + 高并发压测（`han-flash-test` 的 fio 压测是这类雏形），把 1% 复现率拉到 50%+
3. **KUnit / kselftest**：在内核测试框架里写最小触发用例
4. **差分复现**：修复前 vs 修复后跑同一压测，对比 crash 出现率
5. **HITL 复现**：必须人手操作设备时，参照 `diagnosing-bugs` 的 hitl-loop 模板把人工步骤结构化

**判断**：上述任一手段可行 → 进入第 3 步。全都不可行（设备已离线 / 环境无法重建 / 内核版本无法编译）→ 进入第 4 步（记录 finding）。

## 3. 建回路 + 回归测试（可复现类）

遵循 `diagnosing-bugs`（`~/.pi/agent/skills/diagnosing-bugs/SKILL.md`）的 P1-P5 纪律，内核特化版：

1. **建反馈回路**：产出**一条命令**——能跑、能 red（触发这个 crash）、秒级、可重复。非确定性 crash 的目标是"**提高复现率**"而非干净复现（跑 100 遍 / 并行 / 加压 / 注入 sleep，1% 不行 50% 行）
2. **最小化**：砍到最小承重场景（最小输入 / 最少并发 / 最短序列仍能 red），每次砍一个变量重跑
3. **动态证实根因**：在回路上跑——确认复现的就是 Step 7 定的根因（不是隔壁 bug）。**这一步是动态证实静态结论的关键**：若复现出的现象与 Step 7 根因矛盾，回到 Step 6/7 修正
4. **应用修复 + 回归**：应用 Step 8 的 diff → 回路应从 red 变 green → 把最小复现固化为**回归测试**（KUnit 用例 / 触发脚本 / CI 用例）
5. **记录**：复现命令 + 回归测试路径，回填给 Step 9 报告第六档

> **调用 diagnosing-bugs 的两种方式**：
> - analyzer 的 agent 已有完整 crash 上下文，可直接读 `diagnosing-bugs/SKILL.md` 借用其 P1-P5 纪律，在本步骤内执行（推荐，省上下文切换）
> - 或建议用户另开会话跑 `/skill:diagnosing-bugs`，把复现结果带回本会话

## 4. 记录架构 finding（不可复现 / 无测试缝）

若根因是动态行为类但**无法建回路**，或**找不到正确的测试 seam**（内核里常见——probe 顺序 / 中断上下文 / 锁持有窗口 / 硬件时序无干净测试缝），**这本身是 finding**：

- 在报告中新增"架构 finding"档：说明此处内核缺测试缝 / 缺复现手段，根因置信度依赖静态证据链 + 7A/8A 对抗验证
- 该 finding 喂给 Step 10 学习收录，作为"该 crash 类型的测试痛点"

> `diagnosing-bugs` 原文：*"If no correct seam exists, that itself is the finding. Note it."* 内核场景尤其适用——大量 crash 根本没有干净 test seam，承认这点比假装测过更诚实。

## 输出状态枚举（供 Step 9 案例摘要 + feedback-loop JSON 对齐）

本步骤结果用以下 status 值回填报告和案例 JSON（`repro.status`）：

| status | 含义 | 对应根因类 |
|--------|------|-----------|
| `built_loop` | 已建出复现回路 + 回归测试 red→green | 动态行为类（可复现）|
| `skipped_static` | 跳过：静态逻辑类，静态证据链足够 | 静态逻辑类 |
| `skipped_transient` | 跳过：硬件瞬态，物理不可复现 | 硬件瞬态类 |
| `finding_no_seam` | 动态行为类但无测试缝/无法复现，记为架构 finding | 动态行为类（不可复现）|

Step 9 案例摘要"动态复现"字段映射：`built_loop`→已建回路+回归测试；`skipped_*`→跳过；`finding_no_seam`→finding。feedback-loop 步骤 5 仅对 `built_loop` 做 confidence 额外加权。

- [ ] 复现命令 / 回归测试路径 / 架构 finding 已准备好回填 Step 9 报告
