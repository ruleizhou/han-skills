# Step 6: 生成改动方案报告

## 6.1 报告结构（对齐已验证案例文档）

按以下章节组织（参考范本：MT582 案的 `docs/MT582_DDR_1804800_降频方案.md`）：

1. **背景与目标**：原值/目标值表（训练频点 + 运行 DFS 天花板）
2. **现象与根因**：现象演进表（各阶段配置→结果）、死机指纹、根因分层链
3. **终局方案架构**：三层改动关系图（mermaid）
4. **各层改动明细**：每层的 commit / 文件 / 改动要点 / 编译命令 / 产物路径
5. **刷机清单**：镜像↔分区表 + 联刷警告
6. **验证方法**：开机 log 判据 / ramdump 指纹 / RPM 反汇编确认命令
7. **实验对照表**：过程记录（含被证伪的假说——最有价值的部分）
8. **提交索引**：各仓库 commit 列表
9. **FAQ**：能不能只改某一层的问答
10. **路径速查**

## 6.2 必写内容

- **"只刷 XBL+kernel 不刷 RPM 仍会死"** 这类联刷硬约束
- **被证伪假说表**（假说 → 证伪证据），后人不用再猜一遍
- RPM 产物反汇编验证命令（确保改动真编进去了）
